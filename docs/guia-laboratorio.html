🗺️ Metodología Paso a Paso: De Inicio a Fin

Sigue este flujo secuencial estandarizado para asegurar cobertura del 100%, rigor Evidence-First, playbooks deterministas y cero omisiones:

1
Inicialización, Scope Guard & Detección de Desvío DNS (DNS Drift)
Crea la estructura del engagement. SecLab inicializa evidence/, recon/, notes/, scope/ y genera scope/target.yaml con autorización obligatoria (referencia, valid_from y valid_until con zona horaria UTC). El motor monitorea cambios de resolución IP para evitar escaneos hacia activos desvinculados o fuera de alcance. 
# Crear engagement con dominio objetivo:
pt-eng new mi-objetivo target.com
cd /workspace/engagements/mi-objetivo

# Validar que un objetivo o URL pertenezca al alcance autorizado:
pt-eng scope https://target.com/api

# Consultar historial inmutable de revisiones y diffs de target.yaml:
curl -s http://127.0.0.1:8080/api/v1/scope/mi-objetivo/revisions | jq .
🔒 Scope Guard & DNS Drift Activos: Antes de despachar herramientas activas, el sistema verifica la pertenencia estricta al alcance y alerta ante discrepancias DNS. En la terminal libre ttyd rige una frontera operacional explícita para recordar el límite de autorización.
2
Reconocimiento Automatizado, Fuzzing & Trazabilidad (DAG)
Ejecuta la batería de enumeración pasiva y activa: subdominios (assetfinder, findomain), sondeo HTTP (httprobe), scraping de endpoints (gau) y fuzzing de parámetros ocultos con x8. Si ejecutas herramientas manuales por CLI externa, puedes ingestar su corrida en recon_jobs.db para mantener el grafo de procedencia intacto. 
# Reconocimiento continuo con Scope Guard:
pt-recon mi-objetivo

# Fuzzing determinista de parámetros ocultos con x8:
pt-fuzz-params https://target.com/api/v1/user

# Ingestar una corrida manual externa en recon_jobs.db (badge CLI_EXTERNAL):
python3 /usr/local/bin/scripts/seclab_record_job.py record mi-objetivo --tool nmap --target target.com --command "nmap -sV target.com"
3
Playbooks Deterministas & Ejecución Paso a Paso
Ejecuta procedimientos estructurados y repetibles con esquema YAML estricto. El catálogo incluye OWASP Top 10, APIs GraphQL, flujos OAuth/JWT, recursos compartidos SMB y pivoteo interno. Cada paso evalúa Scope Guard de forma fail-closed (código de salida 126 si está fuera de alcance) y admite ejecución simulada (dry-run) o paso a paso con el botón «▶️ Paso». 
# Listar catálogo de playbooks integrados:
python3 /usr/local/bin/scripts/seclab_playbook.py list

# Validar estáticamente un playbook contra el target.yaml del proyecto:
python3 /usr/local/bin/scripts/seclab_playbook.py validate playbooks/api_graphql_audit.yaml scope/target.yaml

# Ejecutar paso individual evaluando Scope Guard en tiempo real:
python3 /usr/local/bin/scripts/seclab_playbook.py run-step playbooks/api_graphql_audit.yaml step_graphql_introspection --context '{"target":"target.com"}'

5
Documentación Evidence-First & Compuertas Bug Bounty
Todo hallazgo debe documentarse con evidencia reproducible, requests/responses HTTP sin alterar y scoring CVSS v3.1. SecLab incorpora compuertas estrictas para descartar falsos positivos y acotar pruebas:
1. Credential Gate Paso 2b / Paso 6
Ante tokens o API keys expuestos, ejecutar llamada autenticada y contrastar obligatoriamente con un Control Negativo (petición sin token o con token alterado). Si ambas devuelven igual respuesta, se descarta como falso positivo.
2. Enrutamiento de Acceso target.yaml
RICH: 2+ cuentas activas → IDOR cruzado bidireccional (A accede a B y B a A).
PARTIAL: 1 cuenta → BFLA y mutación de estado propio.
UNAUTH: Sin cuentas → Superficie pre-auth y fugas en SPA.
3. Bounded Testing (BDT) Regla Operativa
Límite estricto de 1-3 peticiones de prueba por vector. Nunca manipular datos ni cuentas de terceros. Revertir inmediatamente cualquier mutación generada.
4. Ciclo Evidence-First Estados
PROVEN: Verificado con PoC reproducible e impacto demostrable.
CANDIDATE: Vector preliminar sin prueba concluyente.
DISPROVED: Descartado tras test de control negativo.
MITIGATED: Verificado como subsanado. 
# Crear plantilla estructurada de evidencia para el hallazgo:
pt-finding new idor-panel-facturacion

# Validar rigor técnico, PoC y campos obligatorios:
pt-finding lint

# En el visor modal del Dashboard: activa el toggle de redacción de secretos para enmascarar tokens y JWTs.

El estudiante debe responder justificaciones pedagógicas en la pestaña Supervisión del Dashboard, y el docente cuenta con una vista consolidada de cohorte.

# Resumen de cohorte docente (vista agregada de aula):

🎯 Matriz de las 8 Disciplinas Metodológicas

SecLab estructura las pruebas en 8 áreas. Haz clic en los comandos para copiarlos:

1. Recon & Profiling Fase 1
Descubrimiento de subdominios, tecnologías, certificados y superficie expuesta.
pt-recon [target]
2. Param Discovery Fase 2
Fuzzing de parámetros ocultos, scraping de URLs pasivas y paths en endpoints.
pt-fuzz-params [url]
3. Auth & Authorization Fase 3
Matriz de roles, IDORs cruzados, bypass de autenticación, JWT y fallos de sesión.
pt-skills auth-matrix-audit
4. Business Logic Fase 4
Condiciones de carrera, alteración de precios, flujos de carrito y estado.
pt-skills business-logic-audit
5. Inyecciones & SSRF Fase 5
SQLi, SSRF, SSTI, Command Injection con validación fuera de banda (OOB).
pt-callback start 9001
6. Client-Side SPA Fase 6
DOM XSS, postMessage inseguros, fugas de secretos en bundles JS y CSP bypass.
pt-skills client-side-spa-audit
7. API Security Fase 7
Mass assignment, rate limiting, GraphQL introspection y OpenAPI testing.
pt-skills api-security-audit
8. Triage & Reporting Fase 8
Descarte de falsos positivos, severidad CVSS v3.1 y compilación del informe.
pt-report compile
